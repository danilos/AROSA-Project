Technical vision

Capability composition, not another GUI skin.

AROSA aims to make reusable application functionality available through discoverable, versioned contracts while keeping AROS as its operating-system foundation.

The building blocks

ConceptRole
ServiceReusable, lifecycle-managed platform functionality
CapabilityA declared operation, feature or contract offered and requested by components
ProviderAn implementation that supplies one or more capabilities
ConsumerAn application or service requesting those capabilities
AdapterA bridge to existing toolkits, protocols, libraries or system facilities
CompositionResolution of compatible capabilities into a coordinated application workflow

Why this layer exists

AROS provides operating-system mechanisms such as message ports, libraries, drivers and GUI facilities. AROSA works at a different level: registration and discovery, provider selection, authorization, lifecycle, resource semantics and the composition of reusable features. The architecture shares concerns with service-oriented and event-driven systems, but does not claim Kafka's durability semantics, Kubernetes-style cluster orchestration or distributed consensus.

Capabilities flow both ways

An application can consume capabilities and contribute new ones. A graphics tool might expose an image transformation provider; a content manager can supply versioned resources; a document viewer can offer presentation functionality to another application. Sharing is governed by versioned interfaces and appropriate security context.

Cross-cutting responsibilities

Messaging, configuration, logging, time, identity, sessions, authorization, state and resource management support higher-level services. Applications should not create separate incompatible versions of these facilities. Workspaces and personalities affect user experience, not security authority.

A concrete composition example

  1. A file manager requests a document-preview capability for a selected resource.
  2. The platform checks context and finds compatible content, transformation and presentation providers.
  3. The content service selects the correct authorized resource or version.
  4. A qualified provider prepares the representation, and a presentation surface displays it.
  5. Other applications can request the same capabilities rather than duplicating them.

Implementation distinction: this is an architectural workflow. The set of working formats and runtime paths is incomplete and varies by development milestone. Do not infer full office document support from this example.

Built for AROS

AROSA complements rather than replaces AROS, Intuition, Zune/MUI or established native applications. Optional adapters can integrate native mechanisms when available. No claim is made that all existing applications become AROSA-aware automatically.

For technical readers: the public roadmap distinguishes implementation progress from operational maturity. Source-level contracts and detailed integration records are being maintained privately during development.
